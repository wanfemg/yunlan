# 签到分析开发分析

分析日期：2026-11-21（Asia/Shanghai）。本次只分析；未开发功能、未运行测试、未请求实际 NewAPI 实例。下文“拟”表示开发方案，“已确认”表示源码事实。

## 1. 结论与功能定位

新增独立“签到分析”板块，回答四类问题：

1. 多少用户在签到、何时签到、发放多少额度。
2. 哪些用户持续参与、签到后是否继续调用 API。
3. 签到参与者有哪些已观测成功付费行为，钱包充值与订阅分别是什么情况。
4. 哪些数据值得运营复核，以及数据缺失在哪里。

页面沿用 tools 的设计体系，但修正原版的统计口径、跨库查询和数据缺失问题。签到属于运营行为，不把“签到多、调用少、未查到付款”直接等同于恶意、自动封禁或回收额度。

不修改 NewAPI 源码；不增加签到代领、补签、奖励发放或撤销功能。后台已有增删改查权限不意味着本分析模块必须增加写操作。

### 2.1 可可靠读取的签到事实

`checkins` 表只有以下五个字段，`(user_id, checkin_date)` 为联合唯一索引；`checkin_date` 是 `YYYY-MM-DD` 业务日期。[U3]

| 字段 | 含义 | 用途 |
|---|---|---|
| `id` | 签到记录 ID | 排序、明细定位、去重诊断 |
| `user_id` | 账号 ID | 关联账号和调用、付费事实 |
| `checkin_date` | 签到业务日期 | 日趋势、日历、连续签到 |
| `quota_awarded` | 实际发放额度 | 奖励合计和分布 |
| `created_at` | 写入时的 Unix 秒时间 | 明细时间、异常时点线索 |

该表**没有**签到 IP、BrowserID、设备指纹、签到失败、撤销、额度来源余额或具体消费分摊字段。不能从这张表计算“这笔签到奖励具体被哪一次调用消耗”。[U3]

默认签到关闭，最小奖励 1000、最大奖励 10000；启用时在配置区间内随机发放，含两端。历史统计必须累加每条记录的 `quota_awarded`，不能按当前最小／最大奖励反推历史。[U3, U5]

### 2.2 日期、事务与日志边界

上游以 `time.Now().Format("2006-01-02")` 判断当天，受 **NewAPI 进程所在时区**影响；不是浏览器时区，也未在签到表保存时区。签到业务日期以原始 `checkin_date` 为准，调用对比使用的时间边界必须与上游实际时区一致。[U3]

MySQL／PostgreSQL 签到记录创建与用户额度增加在同一事务中；SQLite 路径先创建记录，再增加余额，增加失败时尝试删除记录。其删除错误未单独处理。此处是源码机制说明，不能仅靠现存记录证明所有历史余额发放均已核对一致。[U3]

成功后 controller 另写一条 `LogTypeSystem` 日志，奖励存在格式化文本中。`RecordLog` 并未为这条系统日志填写结构化 `quota`，也未记录签到请求 IP。系统日志写入失败仅写服务日志，不回滚已经完成的签到。**签到表为奖励事实源，不能通过系统日志 `SUM(quota)` 或解析文本替代。**[U4, U6]

### 2.3 接口能力

官方路由为 `GET /api/user/checkin`、`POST /api/user/checkin`，均在 self 路由组，controller 从当前认证上下文取账号 ID；查询接口返回该账号指定月份及历史累计统计。未发现管理员按任意账号或全站查询、补签、撤销签到的现成路由。[U4, U7]

因此站长后台全站分析应读取其既有主库连接中的 `checkins`，而不是循环模拟用户登录或逐账号调用 self 接口。

## 3. tools 现有实现与不能直接照搬的部分

已确认本地参考提供三个 GET：`overview`、`trend`、`freeloaders`，前端包含总览卡、每日柱状趋势和账号列表。[L1–L3]

| 参考实现 | 缺口 | 本项目处理 |
|---|---|---|
| 近 N 日使用日期下界 | 没有结束上界，异常未来日期可能被包含 | 固定业务日期起止和统计时点 |
| 趋势只返回存在记录的日子 | 未签到日期消失，图形易误读 | 补齐每个自然日，真实零值明确为 0 |
| `freeloaders` 只看历史成功钱包充值金额为 0 | 未纳入订阅，也没有“高频”门槛；名称带结论 | 改为中性“签到参与与使用画像” |
| 窗口签到奖励对比 `users.used_quota` | 后者为终身值，窗口不一致 | 所选窗口调用与消费单独按日志聚合 |
| 展示 `users.quota` | 当前余额不等于签到余额 | 标为当前账户余额，不做来源归因 |
| 前端固定除以 500000、两位小数 | 不跟随站点配置，小额显示可能归零 | 读取 `QUOTA_PER_UNIT`，小额保留足够精度 |
| 趋势切换天数后标题仍带 30 日奖励 | 标题与数据窗口不一致 | 文案、图、卡和排行共享范围 |
| 风控 helper 对 `checkins` 执行 `SUM(quota)` | 实际字段为 `quota_awarded`，查询错误被忽略 | 以能力检测与明确错误处理替代静默缺失 |
| 三个前端请求分别读取 | 缺少 Abort、401、状态检查和响应序号保护 | 合并总览与趋势，并保留本项目会话隔离 |

tools 风控中的签到关联 IP 来自调用日志，并非签到现场 IP；不能换个标题后当作“签到 IP”。[L1, L4]

## 4. 本项目集成方式

站长后台目前没有签到模块。其主库、日志库、管理写库可能分别配置；现有后端驱动仅支持 MySQL／PostgreSQL，虽然 NewAPI 本身还支持 SQLite，不能宣称本后台已经具备 SQLite 接入。[L5–L6]

- 主库：签到、账号、成功钱包充值、成功订阅支付事实。
- 日志库：消费日志 `type=2` 聚合额度，调用日志 `type IN (2,5)` 聚合成功与失败请求。
- 后端按 `user_id` 合并两个来源的聚合结果；不能复制 tools 的跨库 SQL JOIN。
- 一次批量聚合全站，不循环调用现有逐用户详情或风控分析造成 N+1。
- 使用全局管理员会话，不引入独立登录口令；不通过浏览器传数据库凭据。
- 表不存在时显示“上游版本未提供签到记录／数据源不支持”，不能新建 NewAPI 表或伪造空统计。

建议文件：

| 文件 | 职责 |
|---|---|
| `backend/checkin_analysis.go` | 能力检测、日期范围、聚合、用户分页与导出 |
| `frontend/src/CheckinAnalysis.tsx` | 独立页面 `/checkin-analysis` |
| `frontend/src/UserCheckinPanel.tsx` | 复用当前用户详情弹窗的签到页签 |

现有用户详情已包含账号概览、调用活跃、登录与尝试、风控四页签；新增“签到”页签显示本账号日历与明细。现有网络事件只允许调用、登录、注册三种来源，登录探针也只负责登录与注册；不得将签到塞进这些来源或借此补造签到设备。[L7–L8]

## 5. 页面拆分与第一版范围

### 5.1 总览与趋势

总览八项：

1. 今日签到人数。
2. 所选窗口签到人数。
3. 所选窗口签到人次。
4. 所选窗口发放额度面值。
5. 人均奖励（窗口奖励／窗口签到人数）。
6. 人次平均奖励（窗口奖励／窗口签到人次）。
7. 已签到账号中的调用活跃人数及比例。
8. 已签到账号中的已观测成功付费人数及比例。

另以“历史累计”独立展示全表累计人数、人次和发放额度，不能混入当前窗口卡。分母为零时比例显示“—”，不显示异常百分比。

趋势在同一图中切换人数、人次、奖励；7／30／90 个自然日及自定义日期范围。缺数据日补零，来源整体不可读时显示不可用，不补成零。

### 5.2 用户排行与参与画像

分页表含账号、签到天数／人次、参与率、发放额度、同期请求、同期成功消费额度、同期成功付费、当前余额、最近签到。支持账号、状态、分组、日期、使用情况筛选及排序。

参与率分母只包括该账号已注册且签到功能可观测的日期；若无法确定功能启用历史或账号注册时间，标记“可观测窗口参与率”，不声称完整资格参与率。

提供“纯白嫖”专门名单，分类依据见 5.5；另提供频繁签到、签到后无已观测调用、低调用等筛选。门槛显示具体定义，运营分类与恶意风险判定分开。

### 5.3 用户签到详情

同一用户弹窗内展示月历、每日奖励、窗口及历史累计、当前连续／历史最长连续签到（有足够历史时）、最近签到记录、同期调用和付费摘要。

连续签到依赖连续业务日期。只读取当前窗口时，只能称“窗口内最长连续签到”；计算真正历史最长需读取相应历史。当天未结束且尚未签到不能直接标为断签或流失。

### 5.4 数据质量与运营线索

单列重复账号日期、未来日期、无效日期、负奖励、孤儿账号、缺表／缺字段和不同数据源覆盖状态。重复签到按业务键用于人次诊断，但奖励金额不得静默去重或丢弃，需同时保留原始记录合计和异常数量。

同账号同秒签到、固定签到时刻、奖励集中等只能作为线索；没有签到 IP／设备就不提供“签到同设备团伙”结论。需要时可展示邻近的已观测登录证据，但必须标明不是签到现场证据，且不能把调用出口当用户位置。

### 5.5 未充值与“纯白嫖”识别（用户追加需求）

增加“纯白嫖”统计卡、名单筛选和用户详情标签。判定范围为全部历史，页面选择的 7／30／90 天只影响签到、调用和消耗等对比指标，不会把以前付过费的用户重新判为从未付费。入口可切换“签到参与用户／全部用户”，不会漏掉未签到但使用注册奖励、邀请奖励或福利码的账号。

分类采用以下规则：

| 分类 | 判定 |
|---|---|
| 已付费 | 历史存在成功、金额大于 0 的外部钱包支付或外部订阅支付，或有站长确认的线下付费事实 |
| 纯白嫖 | 站内付款历史已确认完整、未发现任何成功外部付款或线下付费标记，已经产生正额度消费，且可识别的额度来源全部为免费奖励，没有来源待核实项 |
| 未付费使用／待核实 | 已使用服务、未发现成功付款，但订单历史不完整、存在来源不明兑换码／人工加额，或免费来源无法完整归因；不混入确认的纯白嫖名单 |
| 只领未用 | 已领取免费额度，但完整调用历史中尚无请求；已请求但零额度消费另标“仅零额度调用”，不当成已消耗奖励 |
| 未充值未使用 | 未发现成功付款，也未领取可识别奖励或使用服务；新注册空账号不计入纯白嫖 |

“纯白嫖”为本站数据口径下的运营标签，不保证识别站外交易。数据不足时保留候选名单和具体原因，不能将查询失败、缺表或没有导入历史当成“充值 0 元”。只要已经确认至少一笔实际付款，即使其他历史不完整，也足以排除纯白嫖；反向判断未付费需要完整性依据。

付款识别必须同时处理：

1. `top_ups` 成功外部钱包充值，以及 `subscription_orders` 成功外部订阅支付。订阅在钱包表中的同交易号记账镜像去重；交易金额用精确十进制，不能只按 `users.quota`、`users.used_quota` 或充值日志类型判断。
2. `payment_method=balance` 或 `payment_provider=balance` 的余额购买订阅是内部余额转换，不算一次新的现金付款，也不能凭该订单把奖励余额用户判为付费用户。[U9–U10]
3. 失败、待支付、过期、零金额订单不构成付费事实。历史有成功付款后退款，仍保留“曾付费”；退款金额另列，不用净支付为 0 倒推从未充值。
4. 兑换码有实际使用账号 `used_user_id`、使用时间和额度，但没有销售价格／购买付款字段。付费购买的卡密与免费福利码不能仅凭兑换记录区分；站长在本后台标注“付费码／福利码／待核实”，未经确认的兑换码不自动当成免费，也不自动当成现金付款。[U11]
5. 注册、签到、邀请、管理员加额只有来源明确为免费时才归免费奖励；来源不明的人工加额、线下售卖后手工加额保留待核实，支持本站独立的付费标记，标记不写回 NewAPI。当前表不足以还原的来源不能通过余额倒算。

名单字段：账号、分类及判定依据、历史成功钱包支付、历史外部订阅支付、线下付费标记、已识别免费额度及来源、兑换码来源状态、当前窗口调用／消费、历史已观测消费、当前余额、注册时间、最近使用。默认按所选窗口消费降序，支持历史消费、免费额度和注册时间排序；点击账号仍在当前用户详情弹窗中查看。

总览同时展示“纯白嫖人数／当前窗口消费”“只领未用人数”“待核实人数”，不把消费额度面值称为现金亏损。分类本身不自动封禁或回收额度。

## 6. 统一统计口径

| 口径 | 定义 |
|---|---|
| 统计时点 | 每次请求固定 `as_of`，总览、趋势、排行共享，不边查边移动 |
| 自然日范围 | 日期按上游签到时区；`checkin_date >= start_date AND checkin_date < end_date_exclusive` |
| 调用范围 | 将同一自然日边界转换为 Unix 秒，以 `[start,end)` 查询日志；当前日仅截至 `as_of` |
| 签到人数 | `COUNT(DISTINCT user_id)` |
| 签到人次 | 正常记录按唯一 `(user_id,checkin_date)`；重复记录另报异常 |
| 奖励金额 | `SUM(quota_awarded) / QUOTA_PER_UNIT`，称额度面值 |
| 请求 | 账号已归属的成功与失败业务请求 |
| 消费额度 | 同窗消费日志 `type=2` 的额度合计；退款另列净值口径，不悄悄相减 |
| 成功付费 | 实际成功支付事实；钱包与订阅按 `trade_no` 去除订阅镜像重复 |
| 付费窗口 | 同窗付费与历史付费分开显示 |
| 兑换码与赠送 | 属于额度来源，不自动当作现金付费 |
| 数据缺失 | 缺表、字段不支持、日志不可读均为未知／不可用，不能转成 0 |
| 当前余额 | 当前账户余额，不能归属于签到来源 |
| 关联风险 | 运营线索不自动封禁、不自动回收 |

奖励面值不是供应商实际成本；不能据此计算真实净利润，也不能显示“签到奖励已花完”。没有来源分账时，消费来自充值、签到、兑换码或赠送的具体比例无法准确还原。

## 7. 拟定接口

接口均走站长后台现有管理员认证。

| 接口 | 内容 |
|---|---|
| `GET /api/checkins/summary` | 总览、完整补零趋势、范围、时点、单位、各来源能力与缺失提示 |
| `GET /api/checkins/users` | 同窗用户画像、筛选、排序和分页，返回同一统计口径 |
| `GET /api/checkins/users/:id` | 单账号日历、明细、连续签到及同期调用／付费摘要 |
| `GET /api/checkins/export` | 按当前筛选导出；CSV 内容防公式注入 |

统一响应包含 `as_of`、`start_date`、`end_date_exclusive`、`timezone`、`quota_per_unit`、`mode` 和 `source_status`；不可用的统计使用 `null` 加状态，不以成功空数组掩盖错误。

演示模式单独生成明确标注的签到记录，覆盖未签到、连续签到、中断、不同奖励、调用高低、钱包／订阅付费及未知来源。live 模式绝不注入样本。开发阶段按用户要求不自动执行测试，交付时明确实际完成范围。

## 8. 实施顺序

1. 能力检测与统一自然日／币值口径。
2. 总览趋势及批量聚合。
3. 用户分页、筛选和导出。
4. 当前用户弹窗的签到日历与明细。
5. 中性运营线索和数据质量提示。

第一版做到“看得到、口径一致、能追到原始记录”。自动处置、回收额度、改奖励、代签到不纳入本功能。
